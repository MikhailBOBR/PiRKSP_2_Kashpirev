### Постановка задачи

Разработать небольшое приложение для обработки файлов обмена данными системы поставщиков.

Приложение должно работать с каталогом, в который поступают файлы с информацией о поставщиках или товарах. В качестве входных данных допускается использовать CSV, JSON или обычный текстовый формат.

Для выполнения работы необходимо подготовить не менее **трёх тестовых файлов**, содержащих сведения, например:

> ```
> supplierId
> supplierName
> product
> price
> quantity
> ```

Конкретная структура файла может быть изменена студентом при условии сохранения общей предметной области.

### Требуется реализовать

1. Создать рабочий каталог приложения и средствами `Path` и `Files`:
    
    - проверить его существование;
    - при необходимости создать каталог;
    - получить список содержащихся в нём файлов;
    - вывести имя, размер и время последнего изменения каждого файла.
2. Реализовать поиск входных файлов по расширению, например `.csv` или `.json`.
    
3. Прочитать содержимое найденных файлов средствами Java NIO и выполнить необходимую обработку данных.
    
4. Реализовать копирование или перемещение обработанных файлов в отдельный каталог `processed`.
    

Пример:

> ```
> data/
>     incoming/
>     processed/
> ```

5. Для одного из файлов реализовать чтение с использованием `FileChannel` и `ByteBuffer`.
    
6. Для каждого обработанного файла вычислить контрольную сумму SHA-256 и вывести её вместе с информацией о результате обработки.
    

Например:

> ```
> suppliers_01.csv
> Size: 15428 bytes
> SHA-256: 41A2...
> Status: processed
> ```

7. Добавить наблюдение за каталогом `incoming` с использованием `WatchService`.

При появлении нового файла приложение должно обнаружить событие и запустить его обработку.

Например:

```
Обнаружен новый файл: suppliers_04.csv
```

В качестве предметной области использовать данные из модуля **«База данных АС Поставщиков»**.

Не требуется копировать реализацию базы данных из BootcampLabs. Достаточно использовать аналогичные сущности и поля.

Например, можно использовать сведения о поставщиках или товарах из выполненных заданий BootcampLabs и представить их в виде CSV/JSON-файлов.

### Результат работы

В результате должно получиться приложение, автоматически обрабатывающее поступающие файлы по следующему сценарию:

```
появление файла
→ обнаружение
→ чтение
→ обработка
→ вычисление SHA-256
→ перемещение в processed
```

### Постановка задачи

Разработать небольшое клиент-серверное приложение для передачи данных АС Поставщиков с использованием **RSocket**.

Приложение должно состоять из RSocket-сервера и клиента. Сервер предоставляет данные о поставщиках, товарах или заказах, а клиент запрашивает и получает эти данные в реактивном режиме.

В качестве предметной области использовать данные и сущности из модуля **«Front-end АС Поставщиков»** BootcampLabs.

### Требуется реализовать

1. Создать RSocket-сервер, предоставляющий операции для работы с данными предметной области.
    
2. Реализовать взаимодействие по модели **Request-Response**. Например, клиент передаёт идентификатор товара или поставщика и получает соответствующий объект.
    
3. Реализовать взаимодействие по модели **Request-Stream**. Сервер должен возвращать клиенту последовательность объектов или обновлений с небольшой задержкой между элементами.
    

Например:

> ```
> Товар №1 — 85 000 ₽
> Товар №2 — 42 000 ₽
> Товар №3 — 67 000 ₽
> ...
> ```

4. Реализовать ещё две модели взаимодействия RSocket:
    - **Fire-and-Forget** — для отправки события без ожидания ответа;
    - **Channel** — для двустороннего обмена потоком данных.
5. Добавить обработку ошибок на стороне клиента и сервера. Например, корректно обработать запрос несуществующего объекта.
    
6. Продемонстрировать реактивную обработку получаемого потока на стороне клиента с использованием средств **Project Reactor**.
    
7. Организовать передачу нескольких объектов в рамках одного запроса и продемонстрировать, что клиент получает данные постепенно, а не одним готовым набором.

В данной работе Вы разработаете реактивный HTTP-сервис для получения информации о заказах или доставках с использованием **Spring WebFlux и Project Reactor**.

В рамках работы необходимо реализовать обычные HTTP-запросы и потоковую передачу данных, а также практически показать отличие подхода WebFlux от использовавшегося ранее **RSocket**.

В качестве предметной области продолжить использовать АС сервиса доставки из предыдущих работ.

### Порядок реализации:

1. Создать Spring Boot-приложение с использованием Spring WebFlux.
    
2. Реализовать реактивный API для одной сущности, например:
    

> ```
> Delivery
> ```

с операциями:

> ```
> GET /api/deliveries
> GET /api/deliveries/{id}
> POST /api/deliveries
> PUT /api/deliveries/{id}
> DELETE /api/deliveries/{id}
> ```

3. Для получения одного объекта использовать:

> **`Mono<Delivery>`**

а для получения нескольких объектов:

> **`Flux<Delivery>`**

4. Реализовать реактивную обработку данных с использованием нескольких операторов Project Reactor, например:

> ```
> map
> filter
> flatMap
> switchIfEmpty
> onErrorResume
> ```

**Не использовать `block()` внутри обработки HTTP-запросов.**

5. Реализовать endpoint для потоковой передачи изменений состояния доставки.

Например:

> ```
> GET /api/deliveries/{id}/stream
> ```

Клиент должен получать события постепенно по мере их появления.

Для передачи потока использовать **Server-Sent Events (SSE)**.

Например:

> ```
> CREATED
> ACCEPTED
> IN_TRANSIT
> DELIVERED
> ```

8 практика
  
Разработать итоговое микросервисное приложение, объединяющее основные технологии, изученные в течение семестра.

Необходимо реализовать фрагмент распределённой информационной системы поставщиков и доставки, состоящий из нескольких независимо запускаемых сервисов.

В отличие от предыдущих работ, здесь необходимо продумать не только отдельные технологии, но и **архитектуру всей системы, взаимодействие компонентов, обработку отказов и обмен событиями**.

Можно продолжить проект, разработанный в предыдущих практических работах. **Также возможен выбор собственной темы, в таком случае необходимо согласовать её очно с семинаристом.**

### Требуется реализовать:

Система должна содержать минимум **три бизнес-сервиса**.

Например:

> ```
> Order Service
> Delivery Service
> Supplier Service
> ```

Допускается выбрать другой набор сервисов при сохранении сопоставимого уровня сложности.

### 1. Разделение системы на сервисы

Каждый сервис должен отвечать за собственную часть предметной области и представлять собой отдельное приложение.

Например:

> ```
> Supplier Service
> → поставщики и товары
> 
> Order Service
> → создание и изменение заказов
> 
> Delivery Service
> → доставка и её состояние
> ```

Бизнес-логика одного сервиса не должна напрямую обращаться к базе данных другого сервиса.

### 2. Собственные данные сервисов

Каждый сервис должен иметь собственное хранилище или логически отделённую область данных.

Например:

> ```
> Supplier Service → suppliers_db
> Order Service    → orders_db
> Delivery Service → deliveries_db
> ```

Прямой доступ к таблицам другого сервиса запрещён.

### 3. Единая точка входа

Добавить **API Gateway**.

Клиент не должен напрямую обращаться к внутренним сервисам.

Например:

> ```
> Client
>   ↓
> API Gateway
>   ├── /api/orders
>   ├── /api/deliveries
>   └── /api/suppliers
> ```

### 4. Синхронное взаимодействие сервисов

Реализовать минимум один сценарий синхронного межсервисного взаимодействия.

Например:

> ```
> создание заказа
> → Order Service
> → запрос информации о товаре
> → Supplier Service
> → проверка доступности
> → создание Order
> ```

Для межсервисных HTTP-запросов использовать `RestClient` или `WebClient`.

### 5. Асинхронное взаимодействие

Как минимум один сценарий должен выполняться через **брокер сообщений**.

Пример что можно использовать:

> ```
> Kafka
> RabbitMQ
> ```

Например:

> ```
> Order Service
> → событие OrderCreated
> → Broker
> → Delivery Service
> → создание доставки
> ```

Событие должно содержать только необходимые для обработки данные.

### 6. Обработка повторных событий

Потребитель сообщения должен корректно обрабатывать повторную доставку одного и того же события.

Например, повторно полученный `OrderCreated` не должен создавать две одинаковые доставки.

Способ обеспечения идемпотентности выбирается самостоятельно.

### 7. Обработка отказов

Настроить:

- timeout межсервисного запроса;
- повторную попытку для подходящего сценария;
- Circuit Breaker или аналогичный механизм защиты от постоянно недоступного сервиса.

Можно использовать **Resilience4j**.

При отказе одного из сервисов система не должна зависать на неопределённое время.

### 8. Контейнеризация

Все компоненты системы должны запускаться через Docker Compose:

> ```
> API Gateway
> Order Service
> Delivery Service
> Supplier Service
> Broker
> Databases
> ```

Запуск:

> ```
> docker compose up
> ```

Ручной запуск отдельных сервисов для демонстрации работы не допускается.

### 9. Маршрутизация

Допускается повторно использовать **Traefik** из практической работы №5 как внешний reverse proxy.

Например:

> ```
> Internet / Client
>        ↓
>     Traefik
>        ↓
>  API Gateway
>        ↓
>  ┌─────┼────────┐
>  ▼     ▼        ▼
> Order Delivery Supplier
> ```

Таким образом, Traefik отвечает за инфраструктурную маршрутизацию, а API Gateway - за маршрутизацию внутри приложения.

### 10. Health checks

Каждый сервис должен предоставлять информацию о своём состоянии.

Можно использовать Spring Boot Actuator.

Должна быть возможность определить, какие компоненты системы доступны в данный момент.

### 11. Корреляция запросов

Добавить идентификатор запроса, например:

```
X-Request-ID
```

или `traceId`.

Идентификатор должен передаваться между сервисами и выводиться в логах.

Для одного пользовательского запроса должна быть возможность проследить его прохождение через несколько компонентов.

### 12. Реактивный сценарий

Как минимум один сервис должен использовать технологии предыдущей практической работы:

> ```
> Spring WebFlux
> Mono
> Flux
> ```

Например, клиент может подписаться на изменения состояния заказа:

> ```
> GET /api/orders/{id}/events
> ```

и получать:

> ```
> CREATED
> CONFIRMED
> DELIVERY_CREATED
> IN_TRANSIT
> DELIVERED
> ```

### 13. Полный бизнес-сценарий

Система должна демонстрировать сквозной сценарий работы.

Например:

> **`Пользователь создаёт заказ         ↓ API Gateway         ↓ Order Service         ↓ Supplier Service проверяет товар         ↓ Order создаётся         ↓ OrderCreated         ↓ Kafka / RabbitMQ         ↓ Delivery Service         ↓ создаётся доставка         ↓ статус меняется         ↓ пользователь получает обновления через Flux/SSE`**

### 14. Проверка отказоустойчивости

Во время демонстрации необходимо остановить один из сервисов и показать поведение системы.

Например:

> ```
> Supplier Service OFF
> ```

После этого запрос не должен приводить к бесконечному ожиданию или необработанному исключению.

После восстановления сервиса система должна снова продолжить работу.
